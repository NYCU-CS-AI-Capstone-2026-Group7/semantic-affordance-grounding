## 1. Introduction & Repository Contents

This report describes the development of the semantic grounding layer implemented by Group 07 for the Physical AI robot agent. In robot manipulation tasks, the agent must bridge the gap between low-level raw sensory data (such as RGB-D images and 3D coordinate frames) and high-level abstract goals. Our ontology models the environment objects and semantic grounding for the three baseline courses tasks:
1. **Cup Stacking**: Stacking target cups onto reference locations.
2. **Cutlery Arrangement**: Aligning manipulation targets (knives, forks) with respect to a placement reference (plate).
3. **Toy Block Collection**: Collecting scattered toy blocks and placing them inside a container (basket).

## 2. Ontology Design Rationale & Namespace Policy

### 2.1 Design Rationale & Modeling Logic
The core modeling strategy decouples the static taxonomic description of objects (what the object is, e.g., a cup or a plate) from their task-specific roles (how they function, e.g., target object or reference object) and their action capabilities (what can be done with them, e.g., grasping or stacking). 

* **Physical Entities (`cap:PhysicalObject`)**: Represents the physical things in the environment. We define subclasses like `cap:Cup`, `cap:Knife`, `cap:Fork`, `cap:Plate`, `cap:ToyBlock`, and `cap:Basket`.
* **Affordances (`cap:Affordance`)**: Represents the action possibilities provided by objects to the robot. For instance, a cup has `cap:GraspingAffordance` and `cap:StackabilityAffordance`. A plate provides `cap:SupportAffordance`, whereas a basket provides `cap:ContainmentAffordance`.
* **Task Roles (`cap:TaskRole`)**: Represents task-dependent characteristics. For example, during cup stacking, `g07:blueCup01` acts as a `cap:TargetObject`. In cutlery arrangement, `g07:plate01` acts as a `cap:ReferenceObject`. In toy block collection, `g07:basket01` plays the role of `cap:ContainerTarget`.

By structuring the ontology this way, a robot planner can query the ontology at runtime to determine which object is graspable, where to place an object (reference vs. container target), and what physical parameters (color, width, coordinate frame) to pass to the motion planner.

#### Advanced Features: Hardware-Specific Gripper Constraints
Beyond the baseline requirements, we integrated hardware-specific constraints to ground the agent into real physical limits. We defined the class `cap:EndEffector` and created an instance representing the robot's physical gripper:
```turtle
g07:parallelGripper01
    a cap:EndEffector ;
    rdfs:label "parallel gripper 01"@en ;
    rdfs:comment "The parallel-jaw gripper used by Group 07's robot arm in all three baseline tasks."@en ;
    cap:hasApproxWidth "0.08"^^xsd:decimal .
```
Each graspable target in the environment specifies its physical width using `cap:hasApproxWidth` and references its compatibility via `cap:canBeManipulatedBy`:
```turtle
g07:blueCup01
    cap:hasApproxWidth "0.075"^^xsd:decimal ;
    cap:canBeManipulatedBy g07:parallelGripper01 .
```
This modeling allows the robot to query whether a specific target object fits within the physical limits of its end-effector. If an object's width exceeds the gripper's maximum opening (e.g., if we had a large box with a width of `0.15` meters), the robot could determine that the object cannot be manipulated, preventing mechanical collisions and planning failures.

#### Semantic Richness vs. Flat Labels
To ensure our knowledge graph remains interpretable to both human developers and downstream AI components (such as LLMs that construct task plans from ontology definitions), we avoid flat text identifiers. Every major class, property, and individual is enriched with human-readable metadata:
* `rdfs:label`: Providing a readable, localized string name (e.g., `"blue cup 01"@en`).
* `rdfs:comment`: Describing the purpose, context, or modeling assumptions.
* `skos:definition` & `skos:scopeNote`: Detailing precise semantic definitions and implementation guidelines to prevent manual assertion fallacies.

To prevent vocabulary contamination and ensure clean integration, we maintain a strict separation between shared course definitions and group customizations:

## 4. Key Axioms, Restrictions, and Reasoning Pattern

### 4.1 The Existential Restriction for Graspability
A key requirement of this project is to avoid manually asserting that an object is graspable. Instead, graspability is conceptually modeled using Description Logic (DL):

$$\text{cap:GraspableObject} \equiv \text{cap:PhysicalObject} \sqcap \exists \text{cap:hasAffordance}.\text{cap:GraspingAffordance}$$

In Turtle syntax, we implement this definition using an `owl:equivalentClass` combined with an `owl:intersectionOf` and an existential `owl:Restriction` (using `owl:someValuesFrom` on the property `cap:hasAffordance`):

```turtle
cap:GraspableObject
    a owl:Class ;
    rdfs:label "graspable object"@en ;
    owl:equivalentClass [
        a owl:Class ;
        owl:intersectionOf (
            cap:PhysicalObject
            [   a owl:Restriction ;
                owl:onProperty cap:hasAffordance ;
                owl:someValuesFrom cap:GraspingAffordance
            ]
        )
    ] .
```

### 4.2 Reasoning Pattern: Step-by-Step Trace
To illustrate how the OWL RL reasoner derives graspability, consider the individual `g07:blueCup01`. The reasoning sequence is as follows:

1. **Asserted Facts in Graph**:
   * `g07:blueCup01 a cap:Cup .`
   * `g07:blueCup01 cap:hasAffordance g07:graspingAffordance01 .`
   * `g07:graspingAffordance01 a cap:GraspingAffordance .`
2. **Subclass Hierarchy Inference**:
   * The course ontology defines `cap:Cup rdfs:subClassOf cap:PhysicalObject .`
   * Using subclass inheritance rules (specifically rule `cax-sco` in OWL 2 RL), the reasoner infers that:
     $$\text{g07:blueCup01} \in \text{cap:PhysicalObject}$$
3. **Existential Restriction Inference**:
   * Since `g07:blueCup01` has the property `cap:hasAffordance` pointing to `g07:graspingAffordance01`, and `g07:graspingAffordance01` is of class `cap:GraspingAffordance`, the individual satisfies the existential restriction:
     $$\text{g07:blueCup01} \in \exists\text{cap:hasAffordance}.\text{cap:GraspingAffordance}$$
4. **Conjunction & Class Equivalence Inference**:
   * Because `g07:blueCup01` satisfies both conjuncts, it is classified into their intersection class.
   * By the class equivalence axiom (`owl:equivalentClass`), the reasoner dynamically infers that `g07:blueCup01` belongs to `cap:GraspableObject`:
     $$\text{g07:blueCup01} \in \text{cap:GraspableObject}$$
   * The new triple `g07:blueCup01 rdf:type cap:GraspableObject` is materialized into the inferred graph.

### 4.3 Python Inference Pipeline
We implemented a Python reasoning pipeline (`src/run_inference.py`) based on **Option C** of the course guidelines:
* We load both `course-affordance.ttl` and `group-ontology.ttl` into an RDF graph using `rdflib`.
* We run the OWL 2 RL reasoner by executing `owlrl.DeductiveClosure(owlrl.OWLRL_Semantics).expand(g)`. This computes the deductive closure of the graph under OWL 2 RL semantics, evaluating the intersection and restriction axioms.
* The materialized triples are serialized and exported to `ontology/inferred-results.ttl`, enabling standard SPARQL engines to query the classification results directly.

## 5. Query Results

### 5.1 SPARQL Query 1: Graspable Objects
The SPARQL query `queries/graspable_objects.rq` was executed on the materialized graph to retrieve all inferred graspable individuals:

```sparql
PREFIX cap: <https://hcis.io/ontology/aicapstone/2026/>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT DISTINCT ?obj ?label ?color ?objectLabel ?role
WHERE {
    ?obj a cap:GraspableObject .
    OPTIONAL { ?obj rdfs:label         ?label       . FILTER(lang(?label) = "en") }
    OPTIONAL { ?obj cap:hasColor       ?color       . }
    OPTIONAL { ?obj cap:hasObjectLabel ?objectLabel . }
    OPTIONAL { ?obj cap:hasTaskRole    ?role        . }
}
ORDER BY ?obj
```

### 5.2 Verification and Pitfall Analysis: Exclusion of Reference & Container Objects
Crucially, **`g07:plate01`** (used as a placement reference in the cutlery arrangement task) and **`g07:basket01`** (used as a containment destination in the toy block collection task) are **correctly excluded** from the query output.

* `g07:basket01` is asserted with `cap:ContainmentAffordance` but not `cap:GraspingAffordance`.

Because the reasoner evaluates the existential restriction strictly, only physical objects with a `cap:GraspingAffordance` are classified under `cap:GraspableObject`. This avoids the common modeling pitfall of treating every object involved in a task as a grasp target. By decoupling task roles from physical affordances, we prevent the robot from attempting to execute invalid pick actions on heavy surfaces (like the plate) or large containers (like the basket).

## 6. Design Choices & Discussion

### 6.1 Decoupling Inference and Structural Validation via SHACL
In our implementation, we combined OWL 2 RL reasoning with SHACL validation. This is a deliberate technical choice to handle the differences between the Open-World Assumption (OWA) of OWL and the Closed-World Assumption (CWA) required for execution safety:

1. **Reasoning under Open-World Assumption (OWL)**: OWL assumes that if a piece of information is missing, it is simply unknown rather than false. If we model a cup but omit its coordinate pose frame, OWL reasoning succeeds without throwing an error.
2. **Validation under Closed-World Assumption (SHACL)**: In physical robot control, missing parameters (e.g., failing to specify an object's color, pose frame, or physical width) will crash the motion planners or perception systems. We use SHACL (defined in `ontology/shapes.ttl`) to enforce data completeness.

Our SHACL shape defines strict requirements for physical objects:
```turtle
cap:PhysicalObjectShape
    a sh:NodeShape ;
    sh:target [
        a sh:SPARQLTarget ;
        sh:select """
            PREFIX cap: <https://hcis.io/ontology/aicapstone/2026/>
            SELECT ?this WHERE {
                ?this a cap:PhysicalObject .
                FILTER NOT EXISTS { ?this a cap:EndEffector . }
            }
        """ ;
    ] ;
    sh:property [
        sh:path cap:hasObjectLabel ;
        sh:datatype xsd:string ;
        sh:minCount 1 ;
    ] ;
    sh:property [
        sh:path cap:hasApproxWidth ;
        sh:datatype xsd:decimal ;
        sh:minCount 1 ;
    ] ;
    sh:property [
        sh:path cap:hasPoseFrame ;
        sh:datatype xsd:string ;
        sh:minCount 1 ;
    ] ;
    sh:property [
        sh:path cap:hasColor ;
        sh:datatype xsd:string ;
        sh:minCount 1 ;
    ] ;
    sh:property [
        sh:path cap:hasTaskRole ;
        sh:class cap:TaskRole ;
        sh:minCount 1 ;
    ] .
```

* **SPARQL Target**: We use `sh:SPARQLTarget` to select all `cap:PhysicalObject` instances *except* `cap:EndEffector`. This prevents our robot end-effector (`g07:parallelGripper01`) from being validated against environment-object-specific properties (like `hasPoseFrame`), as the gripper is a persistent hardware component rather than a perceived target object.
* **Property Constraints**: It guarantees that every task object has at least one color, label, width, and coordinate frame. 

Running `validate_shacl.py` outputs `SHACL validation: CONFORMS`, proving that our knowledge graph is structurally complete and ready for safe physical execution.

## 7. Limitations & Future Improvements

### 7.1 Expressivity Constraints of OWL 2 RL in Python
Our reasoning pipeline uses the Python `owlrl` engine, which is restricted to the OWL 2 RL profile. OWL 2 RL is designed for polynomial-time reasoning over large triple stores. However, it lacks support for full OWL 2 DL constructs, such as complex property chains or general cardinality restrictions. If our environment models require highly expressive DL logic, we would have to migrate our pipeline to heavy Java-based reasoning frameworks (such as Pellet or HermiT), which are difficult to integrate into real-time Python-based robotics stacks.

### 7.2 Static vs. Dynamic Affordances
Currently, affordances are represented as static, binary facts asserted in the ontology. In real physical environments, an object's graspability is dynamic and context-dependent. Factors such as kinematic reachability, workspace clutter, joint limit saturation, object orientation, and surface friction determine whether the robot can successfully grasp an object.
* *Future Improvement*: Link the ontology to a geometric simulator (e.g., PyBullet, MoveIt). We can write rules that update the RDF graph dynamically, changing the assertion of `cap:GraspingAffordance` based on real-time spatial checks.

### 7.3 Automated Gripper Compatibility Reasoning
Currently, the relation `canBeManipulatedBy` is asserted manually for each object. It would be more robust to infer this relation dynamically. By comparing the `cap:hasApproxWidth` of the target object with the opening width of the gripper (`g07:parallelGripper01`), the reasoner should automatically determine whether a gripper can grasp an object.
* *Future Improvement*: Implement SWRL (Semantic Web Rule Language) rules or SPARQL construct queries that evaluate numeric conditions (e.g., `objectWidth <= gripperWidth`) to dynamically derive the `cap:canBeManipulatedBy` relation, removing the need for manual compatibility assertions.
